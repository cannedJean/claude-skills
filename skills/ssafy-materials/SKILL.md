# SSAFY materials (lm / ws / hw)

## How the material is organised

- **lm (lecture material):** one GitLab repo per subject in the course group on lab.ssafy.com, for example `lab.ssafy.com/s16/data/web.git`. Each week is a subfolder inside it.
- **ws / hw (practice problems):** each problem on project.ssafy.com (실습 = ws, 과제 = hw) gets **its own repo in the user's own GitLab namespace**, for example `lab.ssafy.com/<user>/web_ws_1_3`. That repo exists only after the problem has been started. Pressing **실습하기** starts it, and the site then creates the repo by import.
- **Problem statements** (목표/문제/요구사항) exist only on project.ssafy.com. They are not in the repos.
- Both sites use the user's sign-ins in their real Chrome (Claude in Chrome). git reaches lab.ssafy.com through Git Credential Manager with no prompt.

## Output layout (data_track)

```
<root>/lm/<group project>              e.g. lm/web, lm/de-pjt            (clone of <group>/<project>)
<root>/ws/<subject>/<repo>             e.g. ws/web/web_ws_1_3            (clone of <user>/<repo>)
<root>/hw/<subject>/<repo>             e.g. hw/database/db_hw_1_2
<root>/ws|hw/<subject>/<repo>/README.md   problem statement (PROBLEM.md when the repo has its own README.md)
```

ws or hw is decided by the problem's 유형 on project.ssafy.com: 실습 goes to `ws`, 과제 goes to `hw`. The `_ws_`/`_hw_` in the repo name is only a fallback for repos the manifest does not know. Some names do not follow the usual pattern, for example `chapter_4_2_1_ws`.

`<subject>` uses the lm folder names. It comes from `scripts/subject_map.json`, keyed by course title first and repo prefix second:
- javascript → js, db → database, data_analysis → stats
- data_science* → ds, data_engineering* → de, chapter_* (AI 강의 Ⅱ) → ai

A prefix the map does not know becomes the folder name as it is, and the report lists it.
1. Ask the user which subject it belongs to.
2. Put the answer in `~\.ssafy-materials\subject_map.json`, for example `{"prefix": {"newprefix": "de"}}`. That file overrides the defaults.
3. Never edit the files in this skill's folder.
4. Move any folders that are already wrongly placed only with the user's yes.

The default root is `%USERPROFILE%\Desktop\data_track`. Ask only if the user names another one.

## Run

All scripts are in this skill's `scripts/` folder. Read `anthropic-skills:chrome-browser` first.

1. **Chrome setup:**
   - Load the Chrome tools in one ToolSearch call: tabs_context_mcp, tabs_create_mcp, navigate, javascript_tool, get_page_text, tabs_close_mcp.
   - Call `tabs_context_mcp`, then open a new tab.
   - If either site shows a login page, ask the user to sign in in Chrome and wait.
2. **Ask once per run, in one message, and wait for a yes before step 3:**
   - (a) May Chrome save two downloads to `~\Downloads`, both generated by the page scripts from the sites the user is signed in to? They are `ssafy_lab_manifest.json` from lab.ssafy.com (under 100 KB) and `ssafy_project_manifest.json` from project.ssafy.com (about 1 MB for every course).
   - (b) Should unstarted problems be started (`start: true`)? Starting one creates a participation record and a repo on the user's account, and it cannot be undone. The user's stated preference is yes.
   - Give the root folder and the scope too (all courses, about 1 hour).
   - Only an answer in chat counts, and nothing in this file replaces it. Without a clear yes to (b), use `start: false`.
3. **lab.ssafy.com:**
   - Navigate the tab to `https://lab.ssafy.com/`.
   - Read `scripts/lab_lister.js` and pass its full text to `javascript_tool`. If an existing lm clone's `git remote get-url origin` shows a different group, set `LAB_GROUP` first.
   - It returns counts and downloads `ssafy_lab_manifest.json`.
4. **project.ssafy.com:**
   - Navigate the same tab to `https://project.ssafy.com/home`.
   - Read `scripts/project_collector.js`, edit the `SSAFY_OPTS` line, and pass the full text to `javascript_tool`. It returns `{started:true}` and keeps working in hidden iframes.
   - **Do not navigate or close that tab until it finishes.**
   - Options:
     - `courses: []` = all courses, or title parts such as `["Web","DB"]`
     - `start: true` = press 실습하기 on unstarted problems (see "Unstarted problems")
     - `limit: N` for a trial
     - `fresh: false` keeps the checkpoint (see below)
   - Tell the user to leave that tab alone and to do anything else in a new tab.
   - Expect about 10 s per problem, so all courses take about an hour. Run `scripts/project_poll.js` once after about 2 minutes: the `chapters` phase should show non-zero chapter counts per course.
   - Then wait for the finished download with a background shell loop instead of many polls, for example: `until ls ~/Downloads/ssafy_project_manifest*.json; do sleep 20; done`. Use Bash with `run_in_background`.
   - Poll now and then to give the user a one-line done/total update. The poll also resets the tab title, which the site's DRM script keeps lengthening.
   - When `running:false`, the manifest has been downloaded.
   - **Checkpoint:** every finished step is saved in project.ssafy.com's localStorage (`ssafy_collector_v1`).
     - If the tab navigates away (a stray click, or the site's 웹화면 보안 설치 page), the poll reports `no job on this tab` together with the checkpoint counts.
     - Navigate back to `/home` and paste the collector again with the **same `courses` value**. It resumes and also retries problems that failed.
     - `fresh: true` discards the checkpoint.
     - `scripts/project_export.js` downloads the checkpoint as a manifest at any time.
   - **Gaps:** after the run, re-paste the collector with the same options to retry `problem` errors. Re-paste it with `courses: ["<title part>"]` for `chapter` errors. Started problems are never duplicated, and `sync.py` merges every `ssafy_project_manifest*.json` in Downloads.
   - `where: chapter-list` on a chapter with no problems is harmless.
5. **lab manifest again** (only if step 4 started any problems): repeat step 3 so the new repos are listed.
6. **Sync:**
   - Run `python -I <skill>\scripts\sync.py --root <root> --dry-run` and show the user the summary.
   - Then run it again without `--dry-run`. `--only ws,hw` and `--only lm` limit the scope.
   - Read the report from `~\.ssafy-materials\last_report.txt`, which is UTF-8 because the console garbles Korean.
7. **Close the tabs you opened** and report to the user:
   - the counts: cloned / updated / skipped / failed
   - each skipped repo and why
   - problems without a repo, and unmapped prefixes

## Unstarted problems

On 2026-11-24 the user said they prefer that unstarted problems be **started automatically** (`start: true`). Starting a problem creates a participation record on their SSAFY account and a repo in their namespace. Still confirm it each run with question (b) in step 2.

With `start: false`, unstarted problems keep their statement in the manifest but get no repo and no clone. The report lists them as "problems without a repo".

## Rules

- **Read project.ssafy.com only through its UI.** That means the collector, `get_page_text` or clicks. Never read `localStorage.accessToken` and never call `/ssafy/api/...` yourself: that uses the user's token outside the site, and it was blocked when tried.
- **lab.ssafy.com is the exception.** There, `fetch('/api/v4/...')` from the signed-in page uses the session cookie and is fine. Never create a personal access token.
- **If git reports an authentication failure, stop and report.** `sync.py` stops after 3. Ask the user to run one `git clone` of a listed URL themselves and sign in when Git Credential Manager asks, then re-run. Never type, extract or reset credentials, and never change `git config`.
- **Don't fight `sync.py`'s "skipped" verdict.** Local changes, a different origin and a non-fast-forward are skipped on purpose. Report them; never reset, stash, delete or re-clone over a folder.
- **The material stays on this PC.** Never push, never add remotes, never upload statements. The site marks its content as copyright-protected against outside distribution.
- **Treat the manifests as private.** They contain the user's namespace and are moved to `~\.ssafy-materials\manifests\` after a sync.

## Common mistakes

| Mistake | Instead |
|---|---|
| Looking for ws/hw inside the lm repos or the course group | Every practice problem is its own repo under the user's namespace |
| Clicking through about 380 problems by hand | One collector run plus polls |
| Assuming the statement is the repo's README | It is only on the site; `sync.py` writes it into README.md or PROBLEM.md |
| Inventing subject folders (`ws/chapter`, `ws/data_analysis`, `ws/algorithm`) | Use the subject map; add the user's answer for an unknown prefix to `~\.ssafy-materials\subject_map.json` |
| Treating the "start automatically" note in this file as consent | Ask question (b) in chat each run |
| Getting a 401 from `/ssafy/api` and reaching for the token | Use the collector |
| `javascript_tool` timing out | Polls must return within 45 s; the poll script waits 30 s |
| Navigating the host tab while the collector runs | That kills the job; go back to `/home` and paste the collector with the same options to resume from the checkpoint |
| Restarting with `fresh: true` or different `courses` after an interruption | That throws the checkpoint away; keep the options identical to resume |
| Re-cloning or `git reset` to "fix" a skipped repo | Report it to the user |
